# Pi 4B candidate on FP-RISC 0.14.0: built and checked, not installed

Date: 2026-11-15. **Status: held by the owner. Nothing on the Pi's installed system changed.**
The Pi still runs the 10 November install (qos `93004f8`, fprisc `20ad433`, ABI 22, codegen 204;
[record](2026-11-10-PI-20AD433-UPGRADE.md)). This note says what was built and checked, why the
install was held, and the steps a full migration needs.

Branch `fprisc-0.14.0-pin` (commit `0241d13` plus this note) carries the pin and the one source fix.
Working files are in `.qos/validation/pi-fprisc-0.14.0-20261115/` (local, not committed).

## What changed in the source

- **Pin**: `fprisc.lock.json` moves from `1b4aca16` to `566870c3`, the commit FP-RISC 0.14.0 was
  built from (tag `v0.14.0`). Codegen revision 239.
- **The inbox wait is a plain reference.** Commit `8134237` declared `fpr_wait_any_until_c` weak in
  `qos/appside/hal.c` and `hal/virt/blk.c`. A weak reference reaches an app image through the GOT,
  which `tools/qa-relocations.sol` refuses (type 311 on AArch64), so no app or plugin built at
  `main`. The runtime at the new pin always has the function, so both files name it directly.

## Why the install was held

None of this is the compiler. Since the 10 November install, QOS `main` itself changed in two ways
that reach the device:

1. **App ABI 22 to 24** (`8134237`: block operations 3 and 4). Every archive built before is refused
   by the new host, including the six onboard apps stored on the writable disk and anything the
   device's Editor builds with its installed SDK.
2. **The compiler daemon was retired.** The host's `Sys.compile` (`qos/portable/compile.c`) still
   talks to a daemon on `/tmp/fprd.sock`, and the Pi's `S98fprd` still starts `qos-fprd daemon` from
   the SDK. The daemon was `tools/fprd.py` on the SDK's bundled Python; both were removed in the
   Sol-only cutover, and the current SDK records `compiler_daemon: false`.

So an install today gives a working Main and six onboard apps, but the Editor can no longer build
and run a program on the device: the old daemon would keep running and produce ABI 22.204 plugins
that the ABI 24.239 host refuses. That is a loss against what is installed now.

## Steps for a full migration

1. **Restore the compiler daemon without Python.** The protocol is the one in
   `qos/portable/compile.c` (Unix socket, peer-credential check, compile, publication, registered
   watches). Sol has no Unix-domain sockets yet, so this is either that support in Sol or a small
   native daemon linking the Editor compiler's `Compile` and `Commit` modules. Keep the name
   `qos-fprd` and the `daemon --socket --work` and `selftest` arguments, so the Pi's
   `/usr/libexec/fprd-sdk-session` and `S98fprd` need no change.
2. **Fix the SDK packager.** `tools/pi4/compiler-sdk.sol` must not strip the runner it is executing
   (strip a copy, or stage `sol` from a second path). Then the SDK must contain the daemon, report
   `compiler_daemon: true`, pass `qos-fprd selftest` in the build container, and stay under the
   40 MiB archive limit and the device's RAM filesystem bounds.
3. **Use a current builder image.** `qos-pi-builder:20261104` (Ubuntu 24.04, GHC 9.4.7, libgit2 1.7)
   can no longer build the compiler, which needs `unix >= 2.8` and `libgit2 >= 1.9`. `debian:trixie`
   with the CI package list plus `clang lld llvm libgles-dev libasound2-dev libdrm-dev libgbm-dev`
   works, and its glibc 2.41 equals the Pi's. Record it as the builder
   (`build-all.sh` and `build-sdk.sh` in the working directory are the commands used).
4. **Rebuild the bundle** from clean exports of the pinned pair: compiler, `main-profile.sol`,
   `portable-es` with ALSA, `runner`, Editor compiler, SDK, `kms-readback`. The policy check needs a
   git checkout, so run it before the export.
5. **Replace the qualification drivers** that were Python: the physical runtime qualification
   (`tools/pi4-build.sol` still builds its bundle; the device driver `check.py` is gone), the Main
   soak with key input, the installed soak and the HDMI readback comparison. Until then an install
   rests on the isolated start/stop checks above.
6. **Migrate the writable disk off the device.** The on-device updater (`update-main-disk.py`) is
   gone and Sol does not run on the Pi. With Main stopped: copy `/var/lib/qosp/Main.disk` off,
   `sol tools/mkdisk.sol --preserve DISK 32` with the six new archives, compare the live keys before
   and after, copy back, verify the hash. Rehearsed today on a copy.
7. **Rebuild user apps.** Any app a user published at ABI 22 must be rebuilt by the new SDK after the
   install. Today's disk holds none beyond the six onboard apps.
8. **Install with rollback.** `install.sh` in the working directory does it from the Mac: verify the
   staged hashes, stop Main, back up the four installed files with a `rollback.sh`, migrate the
   disk, install by rename, start, require "abi v24", six apps, "Main Profile ready" and no
   "abi mismatch", restart once, restore on any failure. It does not touch the SDK or `fprd`; add
   the SDK archive, its hash, the `fprd` stop/start and a daemon probe once steps 1 and 2 exist.
   It has not been run.
9. **After the install**: fresh-SSH verification of the installed hashes, a soak, the HDMI readback,
   an on-device Editor build of a small program, and the record in `docs/`.
10. **Housekeeping.** Three rollback directories remain on the device and the root filesystem has
    285 MiB free; each new one is about 21 MiB. The staged candidate is in
    `/tmp/qos-pi-fprisc-0.14.0-20261115` and disappears at the next reboot, as do the earlier
    deployments' Python helpers in `/tmp/qos-pi-20ad433-20261110`. The Pi's clock is unset.

An install without steps 1 and 2 is possible today with `install.sh`, at the cost stated above.
