# States: the QOS register of intermediate states

Kind: living register, kept current in place. Started 2026-10-08, the
QOS half of fprisc's `docs/2026-10-07-STATES.md` (the actor lifecycle,
the mailbox), following `2026-10-06-FP-RISC-QOS-Reliability-Draft.md`:
every state in which scheduling, failure, cancellation or ownership can
affect correctness gets its owner, what it holds, which events it accepts,
how it is left, and the test that exercises the exit. Statuses are
**Proposed**, **Implemented** (code cited), **Tested** (a test cited),
**Known gap**.

This first entry is the path the draft names as the second target: one
Files request down to the block device and back. Code as of commit
`3fa6600`; function names rather than line numbers, since the FP-RISC
modules move. `std/` and `programs/` are this repository; `F/` is
`../fprisc`.

## 1. A Files request, end to end

### 1.1 The participants and what each one's state is

Five actors and one device take part. There is no shared state object;
each participant's state is a product of its own fields, and a request's
"state" is the tuple of where it is in each.

| Participant | Where | State is | Lifetime |
| --- | --- | --- | --- |
| **Client** | any actor: an app through the namespace (`FS.connect`, `programs/mods/files.fpr`), System.qa directly (`FS.rpc`), a loaded process through the storage syscall (`loader/process.c` `qos_store_call`) | its parked wait on the next message from the Files owner (`sendAwait`: no correlation id on this wire) | the request |
| **Files owner** | `std/fs.fpr` `ownerLoop`, one per disk, hart `diskHart` | `(child, offline)`: the Qlog child's handle or 0, and the latched reason or "" ; plus whether it is inside a request (it serves ONE at a time: `sendAwait` to the child is inside the loop) | the system |
| **Qlog** (the interpreter) | `programs/mods/qlog.fpr` `aLoop`, spawned by the owner on demand | `(head, idx)`: the log head and the in-memory index, rebuilt from the disk by `ensure` and `scanIdxE` at every start; the superblock's write flag `w` and commit flag `c` ON DISK are the durable half of its state | until it stops itself or is killed; replaceable |
| **Block owner** | `std/blockio.fpr` `loop`, one per device, hart `diskHart` | `Owner Active (List Pending) count Mode`: `Active` = `Idle` or `Running from id worker relay cancelled`; the pending queue (bound 64); `Mode` = `Open`, `Closing from id`, `Closed` | the system |
| **Worker and relay** | `blockio.fpr` `io` and `completion`, both `Static 1`, hart 0, one pair per admitted request | the worker is inside `blkRead`/`blkWrite`; the relay is parked on `AC.call worker` | one request |
| **The device claim** | `hal/virt/blk.c` (native): one atomic word, `BLK_IDLE / HELD / ORPHAN / RECLAIMING / RESETTING / OFFLINE`, transitions decided by `hal/virt/blockpolicy.fpr` `ownership`; `hal/unix/blk_raw.c` (Portable): a host worker thread with a time-bounded job queue | the one DMA buffer set and who may touch it | the machine |

### 1.2 Named states, by participant

#### The client

**Requesting** -- `send fs (Rpc me tag key payload)` was accepted
(`std/fs.fpr` `rpc`). The owner's mailbox is `Dynamic 64`, so a refusal
here means the machine is out of memory or the owner is dead; both are
answered, not waited on (`Err "storage service: ..."`).

**Waiting for the owner** -- `receiveFromRes me fs`: parked on the next
message from the owner OR its death. The owner sends its callers nothing
but replies, so the next message IS the answer (the `sendAwait` contract,
`F/std/actor.fpr`). Deadline: none. Dependency: the owner actor, named by
`wait_kind` 3 / `wait_arg` in the runtime register.

- Leaves by: the owner's reply (a `Result String String`, forwarded
  verbatim from Qlog or minted by the owner); the owner's death (`Err
  "dead actor"`).
- Status: **Tested** (every Files test; `tests/qlogowner.fpr` for the
  owner's answers under failure).

**Answered** -- `Ok bytes` / `Ok ""` / `Err why`. The reply is kept into
the client's heap and the message dropped (`replyKept`). What `Ok`
means is below (1.4, U2): an append's `Ok ""` is answered after the
superblock commit write RETURNED from the block owner, which is after
the device reported the page written (native) or `pwrite` returned
(Portable). Neither is a flush.

Through the namespace (`programs/mods/files.fpr`, `EP.simple`): the
client's `readOnce` is `open`, `read`, `close`, three correlated calls to
Files.qa, which forwards one `FS.*` call to the owner. Files.qa holds the
client's handle until `Close` and drops it on nothing else (`EP.simple`
ignores a refused reply; the block endpoint, `blockep.fpr`, is the one
that drops a handle on `"dead actor"`). Status: **Implemented**;
`tests/filessvc.fpr` covers the happy path.

#### The Files owner (`std/fs.fpr`)

**Idle (child, "")** -- a healthy Qlog is bound. **Idle (0, "")** -- no
child yet, or the last one died: the NEXT request starts one. **Offline
(0, why)** -- latched: every request answers `Err "storage offline:
{why}"` at once, forever, until the system restarts. **Shut down (0,
"shutdown")** -- after `quiesce` by the administrator: the gateway stays
alive so bindings get an explicit refusal; Qlog is never restarted.

**Preparing** -- `ownerPrepare`: no child, so spawn `QL.actorWith
(routed block)` on `diskHart` with `Dynamic 64` and probe it with
`stats` (tag 5). Qlog's start runs `ensure` (format or roll back a torn
append) and `scanIdxE` (rebuild the index), both through the block owner.

- Leaves by: `Ok fresh` (Idle with child); `Err why` -> kill the fresh
  child, answer the caller `Err why`, and latch Offline with `why`.
  Recovery is attempted ONCE, on demand, and only one restart per
  failure: "demand-driven ... rather than a background crash loop".
- Status: **Tested** (`tests/qlogowner.fpr`: recovery, no replay,
  latched offline; `tools/qlog-routing-check.py`).

**Forwarding** -- `sendAwait me child (Rpc me tag key payload)`: the owner
itself is parked on the child. During this state the owner serves nobody
else; every other caller's request waits in the owner's mailbox. There is
no deadline on this wait: the owner relies on the layers below to fail
in bounded time (the device deadline, 1.2 below).

- Leaves by: the child's `Result` (forwarded verbatim; child kept); the
  child's death or a refused send (`Err why` -> kill child, answer
  `Err "storage service: {why}"`, child := 0, Offline NOT latched: the
  next request tries once more).
- Status: **Tested** (`tests/qlogblock.fpr`: service death mid-append,
  restart rescans and rolls back).

**Quiescing** -- tag 7 from the administrator (`quiesceOwner`): kill the
child, answer `Ok "quiesced"`, latch "shutdown". `FS.shutdown` then asks
the block owner to `Drain`. Order matters and is stated in the code: the
quiesce acknowledgement comes BEFORE Drain, so Files cannot enqueue new
page I/O behind the drain barrier. Drain settles admitted work; "it does
not assert flush or DMA quiescence". A non-administrator's quiesce is
refused by name.

- Status: **Tested** (`tools/qlog-routing-check.py` boots: "storage:
  Files quiesced and block drained").

#### Qlog (`programs/mods/qlog.fpr`)

**Starting** -- `ensure`: read page 0; if `c` is 0 (a torn append: the
head never moved) rewrite the superblock with `w 0 c 1` -- "truncation at
head IS the rollback"; if unrecognised, format. Then `scanIdxE` walks the
log to the head. Every page goes through the routed block owner
(`pageRead`, `pageWrite`, `pageCount`); a block error here is `stop`
(below).

**Serving** -- `aLoop`: one `Rpc` at a time, tags 1-8. Reads (1, 3, 5, 8)
answer from the index and the pages; appends (2, 4, 7) run the
write-ahead discipline; 6 compacts.

**Appending** (`wrGo`, `wrDo`): (a) `sbW` the superblock with `w 1 c 0`
and the OLD head -- the log is now "write in flight, uncommitted"; (b)
write the header page at `head` and the payload pages after it; (c) `sbW`
the superblock with the new head and `w 0 c 1` -- the commit. Then the
index gains the entry (with its OWN copy of the url, because the message's
url lives in the sender's slab) and the caller hears `Ok ""`.

- Durable point: (c) returning. A crash before (c) leaves `c 0`; the
  next `ensure` rolls back. A crash after (c) is committed. Nothing is
  rewritten but the superblock, so a torn payload page is unreachable
  until committed.
- A full DATA partition is `Err "data partition full"` BEFORE (a):
  nothing is written.
- Status: **Tested** (`tests/qdisk2.fpr`: torn append detected and
  rolled back, hashes verified; `tests/qlogblock.fpr`: a partial append
  on the routed path never continues from the stale in-memory index).

**Compacting** (`compact`, tag 6): copy every live record forward in log
order, then truncate by writing the new head. Idempotent by construction
(positional liveness; the same merkle root). Marked `w 2` while in
flight. Status: **Tested** (`tests/qdisk2.fpr`).

**Stopped** -- `stop why`: a page request answered `Err` (the block owner
refused, the worker died, the device is offline): log at severity 2, kill
MYSELF, and never return ("a partially submitted transaction cannot
continue from an old in-memory head/index"). The owner hears `"dead
actor"` and answers its caller `Err "storage service: dead actor"`. The
block owner and the DMA worker keep their own lifetimes.

- Status: **Tested** (`tests/qlogblock.fpr`, `tests/diskstallp.fpr`
  step 0).

#### The block owner (`std/blockio.fpr`)

**Open / Idle** -- nothing running, queue empty. **Open / Running** --
one request's worker and relay are alive; the queue holds the rest in
arrival order. **Closing from id** -- after `Drain` from the
administrator: nothing new is admitted (`Err "block: draining"`); when the
running request finishes and the queue is empty, `Drained` is answered
to `(from, id)` and the mode is **Closed**. A second `Drain` while
Closing is refused; on Closed it answers `Drained` again.

**Admitting** (`admit`): a `Read p` / `Write p bytes` from anyone. The
queue bound is 64 pending (`Err "block: queue full"`); the sender's
mailbox slot is the `Static 64` ring, a second bound per sender.
`Capacity`, `Status` and `GetBudget` are answered inline, never queued.
`Configure` and `CancelFor` and `Drain` are administrator-only, refused
by name otherwise. Admission is observable: a refusal creates no
obligation; an accepted request is in the queue or Running.

**Starting a request** (`start`): spawn the worker (`io dev`, `Static 1`,
hart 0) and the relay (`completion me worker id q`, `Static 1`, hart 0).
The relay `AC.call`s the worker with the request; the worker does the
device operation and `reply`s; the relay sends the owner `Completed
result`, where a dead worker became `Err "block device: dead actor"`
(`flattenIO`). The owner never touches the device and never parks on it.

**Finishing** (`finish`): only a `Completed` from THIS request's relay
with THIS id is accepted; anything else is ignored (a late relay from a
cancelled request cannot answer a later one). The caller gets the result,
or `Err "block: request cancelled (outcome unknown)"` if `cancelled` is
set. Then `Idle`, and `advance` starts the next pending request.

**Cancelling** (`cancel`, `Cancel target` by the requester or `CancelFor
caller target` by the administrator): if the target is Running, `kill
worker` and set `cancelled`; the relay still delivers `Completed (Err
"block device: dead actor")`, which `finish` turns into the cancelled
answer. If the target is pending, it is removed and answered `Err
"block: request cancelled before I/O"`. Either way the canceller hears
`Ok (Cancelled found)`. Cancellation of a running request is
best-effort and says so: "outcome unknown".

- Status: **Tested** (`tests/blockservice.fpr` via
  `tools/block-service-check.py`: budgets, refusal, recovery, isolation;
  `tests/diskstall.fpr` cancel step).

#### The worker, and the device claim beneath it (`hal/virt/blk.c`)

The worker is a plain actor inside `blkRead`/`blkWrite`. Those are
fail-stop primitives: every bad outcome ends the WORKER (`fpr_actor_fail`),
never the machine, and the relay turns that into a `Result`. The states
below are the device claim's, one word for the whole machine, with the
transitions in `blockpolicy.fpr` `ownership` (state, event -> state):

**IDLE** -- no one holds the DMA buffers. `blk_lock`: CAS `IDLE ->
HELD` (event acquire). **HELD** -- the worker owns the buffers; its
cleanup hook is `blk_abandon`. `blk_rw` posts the descriptor chain and
parks 200 µs at a time until the used ring advances, within the active
budget (`cfg_deadline_us`, default 5 s; `tests` build 0.3 s).

- Leaves by: completion (release -> IDLE; an I/O status byte != 0
  releases then fail-stops "device reported an I/O error"); the deadline
  (abandon -> ORPHAN, then fail-stop "request timed out (the device
  stalled); its buffers stay reserved"); the worker killed
  (`blk_abandon` -> ORPHAN).

**ORPHAN** -- the device may still be writing the buffers; nobody owns
them; they are reserved. Only a later caller's `blk_lock` loop moves on
from here, with `blockpolicy.fpr` `waiting` deciding: if the used ring
shows the orphan complete -> **RECLAIMING** (claim completion: ack the
interrupt, release the buffers, finish -> IDLE, no reset); if the orphan
is older than the deadline -> **RESETTING** (reset the device: status 0,
re-negotiate, rebuild the queue, within `cfg_reset_probes`); otherwise
park and wait. The claim is re-validated AFTER the CAS (`claimStep`): a
completion observed before the CAS may be stale (an orphan-state ABA),
and a stale decision returns the claim to ORPHAN rather than releasing
another request's DMA.

**RESETTING** -- the recovering caller owns the reset; its cleanup hook is
`blk_recovery_abandon`, which on its death or a cancel moves the claim
atomically to OFFLINE ("later callers never reuse a partially rebuilt
queue"). A confirmed reset -> IDLE and "[blk] the device stalled on an
abandoned request; reset, that request was dropped". A reset the device
does not come back from -> **OFFLINE** and the recovering caller
fail-stops.

**OFFLINE** -- absorbing. Every `blk_lock` fail-stops at once ("the disk
is offline (recovery did not finish) -- request refused");
`blkBudgetSet` answers -4. "Reprobing is a separate administrative act"
that does not exist yet.

**Waiting behind a live owner** -- a caller that has waited
`factor` (default 3) deadlines for a HELD claim fail-stops ("exhausted
the configured waiting budget"); the code says this only guards against
a bug.

- Status: **Tested**, thoroughly: `tests/diskstall.fpr` (deadline,
  orphan reset, killed owner, failed reset -> offline),
  `tests/diskresetcancel.fpr` (cancel at both reset boundaries),
  `tests/diskreclaimcancel.fpr` (late completion reclaimed without reset;
  cancel while acknowledging publishes offline atomically),
  `tests/diskclaimrace.fpr` (the stale-claim ABA), `tests/disknative.fpr`
  (concurrent transfers serialise the one buffer), all on legacy and
  modern virtio, one and two harts (`tools/disk-harden-check.py`).

**Portable** (`hal/unix/blk_raw.c`, `qos/appside/hal.c`): a job owns a
copied 4 KiB buffer and two references (caller, worker). **Queued** ->
**Running** (the worker's `pread`/`pwrite`) -> **Done** (published with
release/acquire). The caller parks between checks and gives up at its
deadline (fail-stop; it drops its reference, the worker frees the buffer
when the host call returns, so a submitted write is not rolled back).
**Refused**: a submission while the worker is stalled (its current job
or the oldest waiting one older than the deadline) answers NULL at once;
the queue holds at most what arrives within one deadline. Status:
**Tested** (`tests/diskstallp.fpr`, `tests/diskprogress.fpr`).

### 1.3 Transitions that decide the outcome

| Where | Event | Decision point | Effect on the caller |
| --- | --- | --- | --- |
| client | send to the owner refused | `send`'s Result | `Err "storage service: ..."` at once |
| owner | request while Offline | `strlen offline > 0` | `Err "storage offline: {why}"` at once |
| owner | no child | `ownerPrepare`'s stats probe | success: the request proceeds; failure: `Err why` AND latch Offline |
| owner | child dies / refuses mid-request | `sendAwait`'s `Err` | `Err "storage service: {why}"`; child := 0; NO latch; next request restarts once |
| Qlog | block owner answers `Err` to a page request | `stop` | Qlog kills itself; the owner's path above |
| Qlog | DATA full | `wrGo` before any write | `Err "data partition full"` |
| Qlog | crash between (a) and (c) of an append | `ensure` at the next start | the append is rolled back; the caller had no answer |
| block owner | 64 pending | `admit` | `Err "block: queue full"` to Qlog -> `stop` |
| block owner | Closing | `admit` | `Err "block: draining"` |
| block owner | relay's `Completed` with the right id | `finish` | the result, or "cancelled (outcome unknown)" |
| block owner | `Cancel` of a running request | `cancel` | worker killed -> ORPHAN below; canceller `Ok (Cancelled True)` |
| device | deadline | `blk_rw`'s `blk_expired` | worker fail-stops; relay: `Err "block device: dead actor"`; Qlog: `stop`; owner: `Err "storage service: dead actor"` |
| device | orphan complete / stale | next caller's `waiting`, then `claimStep` | reclaim without reset; stale -> back to ORPHAN |
| device | orphan past deadline | `waiting` -> RESETTING | reset; confirmed -> IDLE, else OFFLINE and fail-stop |
| device | OFFLINE | `blk_lock` entry | fail-stop at once, forever |

The chain of a single device deadline, read bottom-up: worker fail-stops
-> relay `Err "block device: dead actor"` -> owner `finish` answers Qlog
`Err` -> Qlog `stop`s -> Files owner `Err "storage service: dead actor"`
to its caller, child 0 -> the NEXT Files request spawns a fresh Qlog,
which `ensure`s (rolling back the torn append) and rescans -> if its
stats probe fails (the device is OFFLINE), Files latches Offline with
that reason. Three layers each turn a death below them into an answer
above them; none replays.

### 1.4 The draft's universal obligations, for this path

| ID | For a Files request | Status |
| --- | --- | --- |
| U1 ownership | the DMA buffers have one owner at every instant (the claim word); a block request is owned by its worker+relay pair; the Qlog index by the Qlog actor; a reply by its receiver after `keep` | Implemented |
| U2 one outcome | `finish` accepts one `Completed` per id; `sendAwait` takes the next message from the child and nothing else; an append is committed by one superblock write | Implemented; note `Ok ""` means the commit write RETURNED, not that it is flushed (no flush exists) |
| U3 admission observable | block: `queue full` / `draining` by name, nothing retained; Files: offline by name at once; a DATA-full append writes nothing | Tested |
| U4 no stale reference | `finish` ignores a late relay; `claimStep` re-validates after the CAS; `ensure` discards an uncommitted tail; the Qlog index copies urls out of sender slabs | Tested (`diskclaimrace`, `qlogblock`) |
| U5 resolution apart from cleanup | the worker's death answers the relay before the orphan is reclaimed; the Files caller is answered before Qlog restarts; a cancelled request is answered "outcome unknown" while its buffers stay reserved | Implemented |
| U6 every wait names its dependency and deadline | the device wait has a deadline (budget) and a park cadence; the Portable caller has a deadline; the client's wait on the owner, the owner's wait on Qlog and Qlog's wait on the block owner have NONE and rely on the device deadline propagating up by fail-stop | Partial, **Known gap** |
| U7 budgets | 64 pending + `Static 64` per sender at the block owner; the DATA partition bound; the deadline, reset probes and waiter factor, run-time configurable and versioned (`Configure`); the Portable queue bounded by time; no bound on the Files owner's `Dynamic 64` mailbox and no bound on bytes in flight | Partial |
| U8 partial init/shutdown accounted | `ensure` on every start; quiesce before drain, drain before halt; a failed reset leaves the claim OFFLINE and the buffers reserved; a failed Qlog start kills the child | Implemented |

### 1.5 Known gaps

- **Three waits without a deadline.** The client on the Files owner, the
  Files owner on Qlog, Qlog on the block owner. All three resolve only
  because the device wait below them has one and failure propagates up by
  death. A Qlog that loops on a corrupt index, or a block owner whose
  relay never reports, would hang its callers with no escape but the
  deadlock detector, which halts the machine (fprisc register, U6).
- **The Files owner is serial.** One `sendAwait` at a time: a 5 s device
  deadline is a 5 s stall for every Files caller, and the owner's
  `Dynamic 64` mailbox grows meanwhile without bound (U7).
- **`Ok` is not durable.** No flush exists on either tier; the draft's
  "an acknowledgment means durable only after the required device flush"
  is not met and not claimed. `FS.shutdown` says so for drain. The
  register says so here.
- **A reset drops the orphaned request silently to its caller.** The
  stalled request's owner already fail-stopped, so nobody waits; but the
  LOG says "that request was dropped" and nothing else records which
  page. Qlog's `ensure` covers the superblock case only.
- **OFFLINE is terminal with no reprobe.** "A separate administrative act"
  that does not exist (`blk.c`, `blk_recovery_abandon`).
- **Cancel is cooperative.** `Cancel` is checked against the requester's
  handle, `CancelFor` against the administrator's, both "a cooperative
  message convention, not a boundary" (SUPERVISION S7).
- **Portable has no cancel and no admin.** `std/block.fpr`'s budget
  messages answer "native budgets unsupported" there.
- **Files.qa's `EP.simple` holds handles forever** for a client that
  never closes, including one that has died: nothing but `Close` removes
  an entry.

### 1.6 Tests to add, one per exit

A Qlog that stops in the middle of `scanIdxE` (the owner's Preparing
failure path with a real reason); the owner's Forwarding wait with a
child that neither answers nor dies (today: hang); `Drain` with 64
pending; a `Cancel` that races `finish` (the relay's `Completed` arriving
in the same scan); the Portable caller's deadline while the write is
mid-`pwrite` (the write lands after the fail-stop: assert it is visible);
Files.qa's handle table after a client dies holding one.
