# Files and Logs memory investigation

The running Pi appliance reached about 4.1 GiB RSS. Two samples 35.55 seconds
apart grew by 17.46 MiB, about 0.49 MiB per second. Returning to Home without
restarting increased RSS by only 808 KiB over the next 217 seconds. The large
mapping was FP-RISC's arena; the C heap and GPU buffers were small by comparison.

Read-only actor snapshots using symbols from the exact installed archive
identified 1,244,798,880 allocated bytes in the namespace and 308,569,056 in
the directory lister. Their pools had no reclamation boundary. Dropping an
incoming message does not collect temporary strings, tuples or closed-handle
lists allocated in a persistent owner's pool.

There were also 323,784 live message roots, predominantly logging request
tuples and snapshot lists. FP-RISC's log server did not drop request roots,
and `Sys.logSnap` exposed an owned-message obligation through an API that
promised a copy. Both Files and Logs already polled live data before the
scrolling change; this is not evidence that text wrapping introduced the leaks.

## Repairs

- `epservice.fpr` supplies bounded namespace, lister and callback owners.
  Adaptive `std/actor.tidySmall` checkpoints preserve registry entries,
  grants, active handles and complete callback closures. About 32 KiB of
  temporary allocation triggers reclamation, with the threshold adapting
  to live state size. The composition roots and service owners use it.
- `ep.fpr` and its published v1 wire constructors remain unchanged. This
  avoids changing nominal tags in installed, independently built plugins.
  New server code uses `epservice`; clients continue using `ep`.
- FP-RISC logging now returns kept copies and drops received roots. Each
  log-server turn runs in an arena and transfers only its ring state.
  QSys's stateless appkit log adapter also resets its pool between requests.
- A Base-host link hook lets qosp reserve `FPR_HARTS` for the loaded app,
  rather than rejecting four app workers against the host's one-hart cap.

These changes reclaim request history. They do not impose hard byte quotas
on registries, open handles or log contents; those still cost their live size.

## Focused checks

| Check | Old implementation | Repaired implementation |
|---|---|---|
| 20,000 endpoint cycles | 50 MiB retained | Physical Pi: 1.75 MiB additional allocator memory, zero additional roots |
| 2,000 log/snapshot/sequence cycles | 8,000 additional roots | Zero additional roots |
| 20,000 appkit log-adapter snapshots | Not separately measured | Physical Pi: 1.69 MiB additional allocator memory, zero additional roots |

The endpoint check keeps handles open across collection, exercises callback
closures with heap-owned captures, checks grants copied from a scratch arena,
and uses the old pinned client against the new owners. Physical Pi runs pass
with one and four workers under a 128 MiB application arena cap, with clean
exit and no timeout or forced kill. This is a bound on the tested workload,
not a claim of zero allocator overhead. Reproduce with
`python3 tools/ep-memory-check.py`.

The real Linux GL harness passes two boots, Files/Logs scrolling and onboard
plugin/refusal checks. QSys's real disk and plugin path passes two boots.
The endpoint compatibility smoke and native QOS smoke boot pass. The FP-RISC logger fixture also links and
runs on RV64 QEMU; Base logging behavior and arena migration checks pass.

## Physical UI soak and deployment

The deployment archive is built from QOS `335c151` plus these memory repairs,
using FP-RISC `e32e533`. Concurrent app-image and kernel edits are preserved
in the working tree and excluded from this archive.

The physical GPU soak uses four app workers, V3D/EGL, the existing onboard
plugins, a copy of the durable disk, controlled keyboard input and a 128 MiB
application cap. Files and Logs each remain open for five measured minutes
after 30 seconds of warmup.

| View | Measured interval | RSS start -> end | PSS change |
|---|---|---|---|
| Files | 306.44 s | 42,356 -> 42,624 KiB | +268 KiB, then plateau |
| Builtin Logs | 306.76 s | 40,984 -> 40,984 KiB | -1 KiB |

The complete run exits cleanly after 695.68 seconds, with a maximum RSS of
44,884 KiB, no timeout or forced kill, and a durable storage drain. The
namespace and lister occupy one slab each, with about 23 KiB allocated in
the first sampled turn, rather than hundreds of MiB. Live message roots are
20 with a high-water mark of 24 in that snapshot. Captured Files and Logs
screens verify vertical content and changing scroll positions. This is real
Pi GPU rendering into an offscreen buffer; the production scanout is checked
separately after installation.

### Independently loaded Logs plugin

The installed `apps/logs.qa` embeds its own prelude. Updating Main alone
would leave its snapshot ownership bug. A rebuilt Logs archive uses the
same published appkit/endpoint types and the repaired prelude. An offline
installer appends just that archive through Files, reads it back byte for
byte, checks that `apps/index` and Clock/Browser/Disk archives are unchanged,
and drains and flushes before returning. This first passes on an isolated
copy of the actual durable disk. The replacement is 476,971 bytes; the old
archive was 476,916 bytes.

With the updated test disk, the independently loaded Logs plugin runs for
306.97 measured seconds after warmup. Its RSS moves from 42,524 to 42,340
KiB, PSS from 36,651 to 36,467 KiB (-184 KiB). Across all 21 samples PSS
ranges from 35,563 to 36,672 KiB, with no sustained increase. The complete
353.25-second run exits normally and drains storage; peak RSS is 45,800
KiB and peak temperature 63.8 C. Normal/error log filters produce distinct,
nonblank rendered screens. This closes the independently compiled plugin
case as well as the builtin view case.

## Remaining boundaries

These checks establish reclamation for the tested UI polling and logging
paths, not a system-wide memory quota or overnight endurance. Registry size,
open handles and retained log text still require explicit capacity policy.
The separately documented global block actor-identity growth (about 25 MiB
per storage stress workload) is not repaired here. Repeated storage-worker
retirement and bounded dead-identity bookkeeping remain a separate task.
