# Moving QOS's C into FP-RISC: inventory, recipe and order

Date: 2026-11-08. Kind: source inventory, migration plan and revised estimate.
No code change is made by this page.

Baseline: QOS `5feea4b`. FP-RISC pin `e138e654332f9e016a8ee9ffedd330f40cd146c9`
(`fprisc.lock.json`); the sibling checkout used for source inspection was
`6d06ebb`. Line counts are physical lines, `.c` and `.h`, excluding `build/`,
`.qos/` and `__pycache__`. Line references are as of that baseline.

The question this page answers: there is a lot of C in this tree, some of it
vendored dependencies. Which of it can become FP-RISC, in what order, with what
acceptance, and what must stay C?

Short answer: **about 30% of QOS's own kernel-side C is portable now, and the
mechanism to do it already exists and is already in use.** Five real pieces have
crossed: the UART driver, the PLIC, virtio queue setup, block and network
policy, and the archive reader. The rest splits cleanly into "the host OS below
us" (which cannot move) and "vendored data or decoders" (which mostly should
not).

## 2. The rule that decides every file

The tree already has a written boundary, and applying it is mechanical:

> Keep policy and admission in FP-RISC; native code supplies mechanisms and
> system/library adapters. A limit is named policy with a failure result.
> ([design alignment](2026-10-18-QOS-DESIGN-ALIGNMENT.md))

and

> what the runtime or the machine layer implements, the compiler declares; what
> QOS implements, QOS declares -- here.
> ([core/foreign.fpr](../core/foreign.fpr))

So the test for any line of C is not "is it in a C file" but:

1. **Does it name a resource, decide a limit, or sequence a protocol?** Then it
   is policy and belongs in FP-RISC.
2. **Is it a syscall, a device register write, a memory mapping, a thread
   primitive or a GPU call?** Then it is mechanism and stays C.
3. **Is it someone else's data or someone else's decoder?** Then it stays a
   dependency, behind an FP-RISC-declared interface.

`core/foreign.fpr` is where QOS declares every primitive C implements. A
program that names one on a target that does not provide it **fails at link
time**, by symbol: the import list is the capability manifest. That property is
what makes migration safe to do one slice at a time.

The PLIC, virtio and block/network policy units are **raw library units**: they
are compiled `--arc --raw --lib` and their exports *are* the C symbols the
drivers call. That is the recipe in section 6.

## 4. The primitive set a driver needs, and where it is

Everything required to write a device driver in FP-RISC is already a compiler
builtin ([compiler/Infer.hs](../../fprisc/compiler/Infer.hs), the `Mem.*`/`CPU.*`/`Addr`/`Reg` entries):

| Group | Primitives |
|---|---|
| Addresses and words | `Addr`, `Word`, `Layout`, `Addr.add`, `Addr.fromWord`, `Addr.symbol` |
| MMIO registers | `Reg.at`, `Reg.value`, `Reg.setValue`, plus `reg8`/`reg32` over a `device` |
| Raw memory | `Mem.read8/16/32/Word`, `Mem.write8/16/32/Word`, `Mem.alloc`, `Mem.realloc`, `Mem.free`, `Mem.liveAllocations` |
| Ordering | `Mem.fence`, `Mem.atomicExchange`, `Mem.compareExchange`, `CPU.instructionFence` |
| CPU and interrupts | `CPU.csrRead`, `CPU.csrWrite`, `CPU.irqSave`, `CPU.irqRestore`, `CPU.irqEnable`, `CPU.wait` |
| Interrupt routing | `Sys.irqBind`, `Sys.irqUnbind`, `Sys.irqAck`, `Sys.irqDeliver` |
| Allocation-free checking | `profile builtin.` + the `--raw --lib` unit mode, which refuses allocation and recursion |

`Mem.read32` is an inline alignment check plus a volatile load; a failed check
branches to a named panic. A raw unit therefore cannot accidentally take the
allocator, and its instruction and call-site counts are checkable
([native instruction admission](2026-10-23-NATIVE-INSTRUCTION-ADMISSION.md)).

## 6. The recipe

[tests/virtio.fpr](../tests/virtio.fpr) and `hal/virt/qos-virt.mk` are the working
example of the whole loop. Copy this shape for every slice:

1. **Write the unit.** A raw library unit: `profile builtin.`, no allocation, no
   recursion, exported functions taking and returning `Int`, `Word`, `Addr`.
   Example: `hal/virt/virtio.fpr`.
2. **Compile it to an assembly unit with named exports**
   ([qos-virt.mk](../hal/virt/qos-virt.mk)):

   ```make
   QOS_VIRTIO_EXPORTS = probe:qos_virtio_probe,probeAt:qos_virtio_probe_at,...
   $(BUILD)/qos-virtio.s: $(QOS_HAL)/virt/virtio.fpr $(FPRC)
   	"$(FPRC)" --profile=bare-metal-builtin --arc --raw --lib \
   	  --export=$(QOS_VIRTIO_EXPORTS) $< $@
   ```

3. **Add the unit to the link** for all three consumers: the bare-metal image
   (via `EXTRA_RT`), the native kernel ([qos/Makefile](../qos/Makefile)
   includes the file), and `tools/build-process-app.sh`, which invokes it as a
   makefile. `hal/virt/qos-virt.mk` exists so those three name one unit once
   each instead of three times.
4. **Call it from C** through the matching header
   ([hal/virt/virtio.h](../hal/virt/virtio.h)) while the C still owns the
   surrounding mechanism.
5. **Prove equivalence with a differential test** in `tests/host/`, which keeps
   an independent C reference of the *pre-migration* behaviour and runs both
   against fake hardware: [tests/host/virtio_check.c](../tests/host/virtio_check.c)
   programs a bank of fake registers and compares every write.
   [tests/host/netpolicy_check.c](../tests/host/netpolicy_check.c) does the same
   for frames. This is the part that makes the migration safe: the reference is
   written from the old code, not from the new one.

Delete the C only when the differential test covers the whole surface and the
refusal paths, not just the happy path.

## 7. Three blockers, all small, none of them language features

Everything below is a **primitive addition**, not a compiler change.

### 7.1 Aligned DMA memory with a known physical address

[blk.c](../hal/virt/blk.c) `bdata` uses
`static u8 bdata[4096] __attribute__((aligned(4096)))` because virtio requires a
page-aligned buffer the device can address. `Mem.alloc` is `fpr_alloc`: the
buddy/slab allocator, no page alignment, no physical-address notion, and it
reclaims on actor death.

Add one of:

- `Mem.allocAligned(alignment, bytes)` over the buddy, which already has
  power-of-two blocks; or
- a page-aligned static arena window carved by the linker script and exposed as
  a symbol, so a driver can take pages from it (`Addr.symbol` is the existing
  mechanism for naming a linker symbol from FP-RISC).

Either way the page needs **device-visible lifetime**: it cannot be freed while
the device may still be writing to it, which is exactly the ownership rule
`blk.c` enforces today with `waiting`/`resetStep` in
[blockpolicy.fpr](../hal/virt/blockpolicy.fpr).

Also state the mapping: no `satp` is written anywhere in the machine layer, so
virt runs without paging today and an `Addr` is a physical address. That must be
written down as a contract, not assumed, before a driver relies on it -- and it
is the first thing a board port with a PMP or an MMU would break.

### 7.2 Device-ordered memory operations

FP-RISC has three different orderings in play:

| Operation | Ordering today |
|---|---|
| `read`/`write` on a register (`reg8`, `reg32`, `Reg.*`) | `fence io, io` on both sides (`h_read`/`h_write` in [machine/virt/hal.c](../../fprisc/machine/virt/hal.c)) |
| `Mem.read32` / `Mem.write32` and friends | inline aligned load/store, **no** device fence |
| `Mem.fence` | a general fence, not an I/O fence |

`virtio.fpr` brackets its register accesses with `Mem.fence` and a comment, which
works because the differential test proves the programming sequence -- but a new
driver author can get this silently wrong. The fix is an explicitly
device-ordered pair (`Mem.read32IO` / `Mem.write32IO`, or a `Mem.fenceIO`), so
the ordering is in the type, not the convention.

### 7.3 Data-cache maintenance for DMA

RISC-V cores with a non-coherent data cache need clean/invalidate around a
transfer. `CPU.instructionFence` covers the I-cache only. QEMU's virt machine
does not model caches, so it cannot exercise this, and no board in this tree has
needed it yet -- which makes it an untested assumption rather than a solved
problem. Before a driver ships on Star64 or Pi-class hardware, this needs a
primitive and a test.

## 8. Order of work

Each slice is independently shippable and lands with its own test.

| # | Slice | Portable lines | Prerequisite | Acceptance |
|---|---|---:|---|---|
| 1 | GL draw list: walk, sort and stage in FP-RISC, hand C a flat draw list | ~650 | none | byte-identical draw list against the C walker for all onboard scenes; frame time not worse; existing GL suite green |
| 2 | Record framing and scan in `store.c` | ~150 | none | existing app-state acceptance; malformed-record refusal unchanged |
| 3 | Terminal and evdev decode | ~250 | none | the same keycodes and modifier bias from a tty, a FIFO and a real `eventN` |
| 4 | Pin bus | ~100 | none | `std/gpio.fpr` tests; level/read-back |
| 5 | Loader bookkeeping: slot, quiescence, relocation policy | ~265 | none | placement refusal before any write; image-wide quiescence |
| 6 | virtio block queue, descriptor chains, completion | ~500 | 7.1, 7.2 | differential test on fake rings; power-cut and orphan-reclaim legs; the existing `storagedeadlines`/`filesreclaim` suites |
| 7 | virtio net queue and frame path | ~480 | 7.1, 7.2 | frame-level differential test; deadline and offline transitions |
| 8 | Interrupt-driven completion instead of polled | -- | 7.3 on real boards | latency under load; no missed completion; board soak |

Slices 1 to 5 need no new primitives and can start today. That is roughly
**1,400 lines** with no hardware risk, including the single largest file in the
tree.

## 9. What stays C, and why

| Layer | Why it cannot be FP-RISC |
|---|---|
| `open`/`pread`/`pwrite`/`ioctl`/`mmap`/`poll` (`hal/unix/*`) | these *are* the host operating system; FP-RISC's `std/os` declares them and a board fails the link by name |
| `pthread_*` (`park.c`, `host.c`, `store.c`) | the host's threading; FP-RISC sees only the doorbell |
| EGL, GLFW, GL, CoreAudio, evdev ioctls | foreign libraries with their own ABI |
| `fork`/`exec` and the socket bridge (`compile.c`) | process control |
| `drm_scanout.h` constants | they are the Linux UAPI; a second copy in FP-RISC would drift, not decouple |
| `font_sdf.h` | generated data, not code |

Two more that look portable but are not worth it yet:

- **Byte-level copies and framing on bulk data.** FP-RISC byte and string loops
  are 11-31x C on the same box
  ([6 November remeasure](../../fprisc/docs/2026-11-06-PERFORMANCE-AT-E138E65.md)),
  so moving a framebuffer copy or a multi-megabyte scan would be a straight
  regression. Move the *decisions* about those copies, not the loops. When the
  byte-loop and SHA gaps close, revisit.
- **[sha256.c](../qos/portable/sha256.c) versus [std/digest.fpr](../../fprisc/std/digest.fpr).**
  Two SHA-256 implementations is a real problem, but porting the C one is the
  wrong fix: it is on the *launch* path hashing whole images
  ([host.c](../qos/portable/host.c), `qosp_sha256` on attach), and the FP-RISC digest runs at about a
  megabyte a second. The fix is architectural -- verify at install, once
  ([zero-overhead OS](2026-11-06-ZERO-OVERHEAD-OS.md), move 10; the current
  joint order is owned by [the amended page](2026-11-06-ZERO-OVERHEAD-OS-AMENDED.md),
  which confirms the launch re-hash as its C11) -- after which the C hasher is
  only needed for artifacts that arrive unverified.

## 10. minimp3: a decision, not a port

`minimp3.h` is the only vendored *code* dependency in the tree. Three options,
ranked by what they cost:

1. **Keep it, behind a narrow declared interface.** Cheapest. It is public
   domain, it is 1,865 lines, and it is already only reachable through
   `sndMusic` in [core/foreign.fpr](../core/foreign.fpr). The tree then has one
   vendored decoder and says so.
2. **Write a Layer III subset decoder in FP-RISC** (~700-1,000 lines) and keep
   minimp3 as the differential oracle -- decode the same files with both and
   compare PCM. Choose this if the goal is "no third-party code in the tree"
   rather than performance. Expect it to be several times slower: the hot path
   is MDCT and polyphase synthesis in float, and floats are boxed on RV32.
3. **Port minimp3 faithfully.** Almost all of the effort of option 2 with none
   of the leanness, and the same slowdown. Not recommended.

Whatever is chosen, the interface should be the one already in place: an FP-RISC
signature in `core/foreign.fpr`, so removing the dependency later is a link-time
change rather than an editing sweep.

## 11. What this buys, honestly

Wins:

- One ownership and linearity story for the whole system, not two.
- Driver state machines become checkable: allocation-free, bounded, with
  instruction ceilings.
- `core/foreign.fpr` shrinks toward the actual host boundary, so the capability
  manifest stops overstating what a program can reach.
- The "policy in FP-RISC" rule stops having exceptions, which is what makes it a
  rule.

What it does not buy:

- **Isolation.** A driver in FP-RISC panics in the same runtime it runs in, just
  as the C does today. There is no MMU or privilege boundary either way
  ([architecture audit](2026-09-29-QOS-ARCHITECTURE-AUDIT.md)).
- **Speed.** Every slice here is neutral-to-slightly-slower than C on the current
  compiler. If a slice is materially slower, that is a compiler finding, and it
  belongs in FP-RISC's performance plan rather than being absorbed by keeping
  the C.
- **Fewer bugs by construction.** The differential test is what prevents
  regressions; the language makes the *bounds* checkable, not the protocol
  correct. Write the reference test from the old code first.

## 12. Limits of this page

No build, benchmark or differential test was run for this assessment. The line
counts are physical lines at the stated baseline. The per-file "portable"
figures are region estimates from reading the sources, not measurements; the
method is stated in section 5 so they can be checked or replaced. Nothing here
claims that the three prerequisite primitives are the only ones the driver
slices will need.
