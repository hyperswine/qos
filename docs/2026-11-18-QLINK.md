# qlink: the UART link to the host, and Spectre-84's console over it

Date: 2026-11-18. Kind: implementation record, milestone M3 of the Spectre-84
plan. Sources: QOS `88000de`. Limits the design follows were measured in
[the spikes](2026-11-18-SPECTRE-84-SPIKES.md).

## Protocol (`hal/link/qlink.h`)

One checked byte stream carrying channels, the same C on board and host:

    7E | ch | seq | ack | len | payload | crc16 | 7E

- 7E, 7D and 03 inside a frame go as 7D, b ^ 20. A raw 03 resets
  Simple-Risc cores outside their ROM, so it never appears in a frame.
- CRC-16/CCITT-FALSE over ch..payload.
- `ch`: channel in bits 0-5 (control, console, input, display, clock, files,
  audio, log); bit 6 ack-only; bit 7 unreliable (never resent: display
  tiles, log lines).
- Reliable frames are go-back-N: a window of frames in flight, resent after
  a timeout; `ack` is the last frame received in order.
- A host opening the link sends an unreliable control `HELLO`; the board
  starts a new session (both sequence spaces at 0) and answers `HELLO`.
- Bytes outside frames (the ROM's lines, a panic) reach the host as raw text.

The board sends at line rate with a window of 4. The host keeps one frame of
at most 14 payload bytes in flight and writes it in pieces of at most 24
bytes, 3 ms apart: the Tang Nano's USB bridge drops board-to-host bytes when
one host write is large. Waiting for each ack also means a host frame can
never overrun the board's 32-byte receive FIFO, however late the board polls.

## Code

| File | Role |
|---|---|
| `hal/link/qlink.c` | frame codec and session |
| `hal/link/qlink_sruart.c` | board side over Simple-Risc's UART, console channel (`qcon_putc`, `qcon_getc`, `qcon_flush`, `qcon_drain`) |
| `tools/qhost/qhost.c` | host: `attach` (interactive console, Ctrl-] quits) and `script` (`send-line`, `expect`, `soak N`, `delay`) over a serial port or `unix:/path` |
| `tools/qhost/qlink_test.c` | two endpoints over a wire that drops and corrupts bytes |

The Spectre boot image runs its console over qlink when built with
`SPECTRE_CONSOLE=qlink`; `raw` stays the default so the existing board checks
(which drive the plain prompt through `spectre-uart`) keep working. The image
gained `soak N`: N numbered lines, each carrying 03, 7E and 7D.

    cc -O2 -Ihal/link -o qhost tools/qhost/qhost.c hal/link/qlink.c -lm
    qhost attach /dev/cu.usbserial-20250303171 --mhz 84
    qhost script PORT --mhz 84 send-line ls expect notes/spectre.txt 10

## Results

- **Unit test:** every reliable message arrives once and in order in both
  directions with no loss, 0.2% loss, 0.2% corruption, 0.5% of each, and 2%
  loss with 1% corruption; no raw 03 reached the simulated wire.
- **Board (Spectre-84, from SRAM, FP-RISC runtime `69da12ca`):** `ls` and `cat`
  through qhost; reopening qhost starts a new session; a 12,000-line soak
  (996,890 bytes) in 116.7 s, 8,541 B/s, with no loss, no CRC errors, no
  duplicates and no resends (about 88% of the 9.68 KB/s line); a command
  holding a raw 03 arrives intact and is rejected by the prompt, and the core
  does not reset.

## The time wrap (not qlink)

After about 107 s of uptime the next storage call panics:
`Int overflow: 1073741823 - -37439313`. RV32 Int is 31 bits; `Sys.mtime`
returns the 10 MHz timebase truncated to it (`fprisc/runtime/actors.c`), and
`std/actor`'s deadlines compute `intMax - now` from it. The soak runs past
107 s, so a command after it trips the panic. The same panic was already
known on Spectre-54. It cannot be fixed in QOS alone: QOS pins `std/actor` as
a frozen store module, and a change of time units under it would stretch
every deadline. The fix (time and deadlines for 32-bit targets) is milestone
M5's and blocks long Shell.qa sessions.
