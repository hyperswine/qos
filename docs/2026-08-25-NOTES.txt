=================

Memory Subsystem.

Buddy allocator for managing memory in power-of-two blocks as the global allocator at the very bottom.
Slab allocator for managing small objects efficiently on top of the buddy allocator, on a per actor basis.
Each actor is an ACB (Actor Control Block) that manages its own memory using the slab allocator.
The code in the ACB - the .program stuff should implicitly use the actor's slab allocator for memory management in a soft runtime
So each actor basically has its own soft runtime with an Rc and Slab allocation mechanism basically integrated into its .program code
rather than an external or explicit thing

This basically means, when we call something like `x = Cons y z` this needs an Rc and slab allocation for the new cons cell.
But this happens implicitly, and basically just links in the C backend allocator function almost like a vDSO but no virtual memory, just a direct ABI memory call to *alloc and *dealloc and *rc and *unrc.
it can be seen like x_mem = (*vdso.alloc sizeof(Cons)); x_rc = (*vdso.rc x_mem); *x_mem = (Cons){y, z}; x = x_mem; x.
The entire lifecycle of the Rc and memory is inserted into the .program, no extra "runtime" or "kernel" required

=================

Disk Subsystem.

As described in DISK.txt

The data is a recursive chunk based system.
Each chunk has a header and body, with a hash
"Files" are just a higher level concept managed by things like System.qa and Files.qa and typically map a URL to an ID
By folding all the chunks with that ID, you can get the file's data

Almost everything else is built ontop of this
Any "driver code" is basically just a file managed within this recursive chunk system that can be loaded into memory as executable code for some service actor

=================

Scheduler.

The scheduler is inherently a decentralized mesh topologically speaking.
There is no one global scheduler. Rather each hart or executable processor manages its own local scheduling decisions and communicates with other harts to coordinate task execution.
The design is meant to be straightforward, so there shouldnt be any big issues with the implementation.

Each hart maintains a set of <runqueue, ready, backlog> queues.
The runqueue is a queue of size N tasks that are currently being executed or are ready to be executed.
The ready queue holds tasks that are ready to run but are waiting for their turn.
The backlog queue contains tasks that are waiting for some condition to be met before they can be moved to the ready queue.

=================

IPC. Interprocess Communication.

Almost all native IPC on QOS and within native FP-RISC applications are done through message passing and actors.
Each actor is backed by an ACB. The ACB contains a record of {(pid, actor_id) : (incoming queue, outgoing queue)}
They are SPSC buffers. And the boundary condition - when full, is decided by the policy implemented in the actor, which could involve blocking, dropping messages, or other strategies.
That policy should be defined with a `receive { ... Fail -> ... }` block.

=================

Application System.

The application system is higher level and is not even technically QOS itself.
But the QA format, aka the Quick Archive format is the default format for storing and managing application data within the system.

To abide by this format, one should have certain pieces of metadata
With a specific kind of entry point that allows easy startup
It also defines a supervisor and certain signals that must be accepted
As well as permissions required for accessing various system resources.
These all have to be declared upfront

=================

Startup and Shutdown.

The startup is basically like a way to bring up the bare metal system into the base assumption state for FP-RISC.QOS QA format applications to start running.
So it basically just has to do whatever minimal stuff for the first .QA services to work, such as System.qa, Memory.qa, Files.qa. Loader figures it out.

There is a simple sleep mode that just puts all processors on low power until an interrupt or other wake-up event occurs.
As well as any peripheral power management, ensuring that unused peripherals are also put into low power states to conserve energy.

Shutdown is the process of bringing the system down from its operational state to a safe and low-power state. This involves stopping all running tasks, saving necessary state information, and ensuring that all peripherals are properly powered down. The goal is to leave the system in a consistent and recoverable state for the next startup.

=================

Services.

All services on QOS are mapped to the URL-VFS by System.qa. They are addressed by a URL in /services such as /services/keyboard.
All services are just .qa applications that are like any other app, but have more specific WCET and declarative resource requirements including more privileged permission wants.
Services are just an application that abides by the QA format. They have a supervisor, and are typically a sort of model-update genserver.
They may have quite a few actors, and typically a single main actor that talks with other clients. Typically the service_pid.main_actor.
